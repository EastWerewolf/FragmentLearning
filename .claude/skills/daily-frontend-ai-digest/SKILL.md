# 每日一推 · 前端 / AI 每日精选

## 何时使用
当用户要求「每日一推」「每天搜索前端 / AI 值得关注的内容并更新到项目」「每天更新前端动态」等时使用。

## 目标
每天生成**一个** Markdown 文件，汇总前端与 AI 领域**最新**、值得关注的内容，并做**本地提交**（不推送）。

## 两条硬性要求（最重要）
1. **尽量最新**：只推近期（默认 1–7 天内，越新越好）的动态。优先「刚刚发布 / 本周发生」的消息；老内容、已被广泛讨论过的内容不再收。文件里每条都带上日期或版本号，便于判断新鲜度。
2. **不要重复**：动手前先读 `md/每日一推/` 下**最近 3–5 个文件**，把已经推过的条目、项目、版本记下来；本次不再收录。同一主题若确有**新进展**（如某工具出新版本），只写新进展，并注明"此前于 <日期> 推过"。

## 输出位置与命名
- 目录：`md/每日一推/`
- 文件：`YYYY-MM-DD.md`（**一天一个文件**，互不合并，按日期命名）
- 示例：`md/每日一推/2026-10-16.md`
- 若目录不存在则新建；不要把所有内容写进同一个累积文件。

## 内容范围
- **前端**：语言规范（TC39 / ECMAScript）、框架与构建工具（React / Vue / Vite / Rolldown / TypeScript 等）、浏览器新特性（Chrome / Safari / Firefox / Edge 发布说明）、CSS 与 Baseline、性能与 Core Web Vitals、工程化、值得一读的好文。
- **AI**：AI 编程与 Agent（Claude Code / Cursor / Copilot / Codex / Gemini CLI 等）、AI SDK、模型发布、MCP 生态、AI 与前端的结合。
- 每天约 8–15 条，分节组织；每条一句话说明 + 一个可达链接；中文为主。

## 文件模板
```markdown
# 每日一推

> 每日整理前端与 AI 领域值得关注的内容：新规范、框架/工具发布、浏览器特性、AI 编程与 Agent、好文。
> 一天一个文件，由定时任务自动更新。

## YYYY-MM-DD

**一句话速览**：……

### 🌐 语言与规范
- [标题](链接)（日期/版本）：一句话说明。

### 🚀 框架与工具链

### 🎨 浏览器与 CSS

### 🤖 AI 与开发

### 📚 好文精选

### 🧰 其他值得关注

### 📌 参考来源

> 说明：条目来自近期公开报道；实验性特性以实际浏览器支持为准。
```

## 流程
1. **查重**：先列 `md/每日一推/` 现有文件，读最近 3–5 个，整理"已推清单"。
2. **搜索**：用 WebSearch 搜索近 1–7 天动态。推荐检索词：
   - 前端：「前端 值得关注 <年月>」「前端周刊」「Vite / React / Vue 发布」「Chrome / Safari release notes」「Baseline CSS 新特性」
   - AI：「AI 编程 Agent 发布」「MCP 生态」「模型发布」「AI coding agent news」
   - 聚合源：前端周刊（frontendweekly.cn、weekly.shanyue.tech）、InfoQ、Chrome for Developers、WebKit / Apple 发布说明、TC39、web.dev。
   - 目标是最新一期/最近几天，优先更新鲜的来源。
3. **验证**：优先官方来源；对关键链接用 WebFetch 抽查可达（HTTP 200）；与已推清单比对去重。
4. **生成**：按模板写入 `md/每日一推/YYYY-MM-DD.md`。
5. **本地提交（不推送）**：
   ```bash
   git add "md/每日一推/YYYY-MM-DD.md"
   git commit -m "每日一推：YYYY-MM-DD"
   ```
   - **只 `git add` 当日文件**，不要 `git add -A`（仓库存在大量行尾差异的「脏」文件，全量提交会污染历史）。
   - **不要执行 `git push`**：推送由用户自己在本地/Windows 完成。生成文件 + 本地提交即为完成。

## 环境限制与回退（重要）
- **不推送**：本任务只做本地提交；不要尝试 `git push`（沙箱无 GitHub 凭据，且按用户约定由用户自己 push）。
- 沙箱**禁止删除文件**（`rm` / `unlink` 返回 `Operation not permitted`），会破坏 git 的锁机制，使 `git add/commit` 反复在 `.git/` 留下 `index.lock`、`HEAD.lock`、`refs/heads/*.lock`。若必须在无删除权限的环境里提交：
  - 每次 git 操作后，把残留的 `.git/index.lock`、`.git/HEAD.lock`、`.git/refs/heads/*.lock` **重命名**（如加后缀 `.stale`，**不能删除**）再继续；否则后续 git 命令会因 `File exists` 失败。
  - 只用重命名（`mv`）而不是删除来清理，因为该环境不允许删除。
  - 提交完成后务必确认 `.git/` 下不残留 `*.lock`，以免阻塞用户后续的 git 操作。
- 在普通本地环境（如 VS Code 中直接运行）通常没有上述限制，正常 `git add` / `git commit` 即可，`git push` 也交由用户自行执行。

## 注意
- 只写高信号、值得关注的内容，不堆砌。
- 链接必须可达；不确定的传闻标注「未独立验证」。
- 严格遵守「一天一个文件」「尽量最新」「不重复」。
