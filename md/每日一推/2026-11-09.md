### 🎨 浏览器与 CSS

- **[TPAC 2026 的四项 CSSWG 决议：shrinkwrap 终于立项，`vertical-align` 多了个 `cap-middle`](https://blog.kizu.dev/four-tpac2026-csswg-resolutions/)**（TPAC 2026 于 **10-26 ~ 10-30** 在都柏林举行，Roma Komarov（kizu）远程参会后本周整理成文）：比「又多了个属性」更有价值的是看 CSSWG 怎么给拖了十年的问题收口。**一、shrink-to-fit / shrinkwrap**——「让盒子宽度贴合内容、但不换行」这个需求从 2016 年（yisibl 提的 issue）挂到现在，一直没有纯 CSS 解；本次 **RESOLVED：作为新关键字，或修改 `fit-content` 与自动尺寸语义来解决**，Google 的 Kent Tamura 与 Ian Kilpatrick 在原型实现。对做过「标签自适应宽度」「卡片横排不换行」的人，这是最值得盯的一条。**二、`vertical-align: cap-middle`**——按**字体大写字母高度（cap-height）的中点**对齐，而不是按行盒中线；Tyler Sticka 2020 年提的 issue，解决的是「图标和文字视觉上永远差半像素」这类对不齐的老毛病。**三、`param(color)`**——把当前 `color` 通过 linked parameters 传进嵌入内容（典型场景：让内联 SVG 图标自动跟随文字颜色），实现方式是在 UA 样式表里写 `:root { color: env(color, CanvasText) }`；Lea Verou 提的 issue，与之相关的一个时序问题（Elika J. Etemad）仍未解决。**四、`@property` 的简写注册**——支持简写自定义属性，但列表、可省略的初始值、`inherits` 等细节仍部分未定。⚠️ 这四条都是**决议（RESOLVED）不是实现**：方向定了，规范文本、WPT 与浏览器落地都还在后面，短期内不能当可用特性写进生产代码。

### 🚀 框架与工具链

- **[Vite+ 1.4.0：`vpx` 可以直接跑 TS，`vp migrate` 能把 tsx 整个换掉](https://github.com/voidzero-dev/vite-plus/releases)**（v1.4.0 于 **10-23** 发布，本周 JSer.info #782（11-09）才把它汇总进视野；之所以仍然值得看，是因为它改变的是「跑一个脚本」这件最日常的事）：**`vpx` 现在能直接执行 TS / JS 文件，不再需要 `tsx`**，并支持 **`vpx --watch <file>`**——文件或其导入、tsconfig 变化时自动重跑，底座是 oxc-node 的 watcher。迁移路径也铺好了：**`vp migrate` 支持从 `tsx` 迁移**，会把 `package.json` 脚本里的 `tsx` 改写成 `vpx`、`tsx watch` 改写成 `vpx --watch`、删掉 `tsx` 这个 devDependency，并把 `node --import tsx` 换成 `node --import vite-plus/register`。兼容性上它接受 `tsx watch` 的常见参数（`--ignore`、`CHILDREN_USEPOLLING`、`--watch-preserve-output`、`--watch-kill-signal`），另有自己的 `--include` / `--exclude` / `--poll` / `--tsconfig` / `--kill-timeout` / `--rerun-on-enter`。其余小改进：`vp check --deny-warnings`、`vp pm team` 管理 registry 团队、独立 `vp` 二进制小约 **30%**，以及一批缓存命中率与 Windows Ctrl+C 退出码的修复。⚠️ **迁移有几个真实坑**：JSX runtime 默认值、`.cts` 的处理、CJS 包里 `import` 的语义、`require()` 的解析行为、信号与退出码都与 `tsx` 不完全一致；Node 版本要求 `^22.18.0 || ^24.11.0 || >=26.0.0`；`vpx` 脚本跑在 **oxc-node@1.0.0** 上，还不到 `.0` 之后的稳定期。

### 🤖 AI 与开发

- **[Apiiro：Claude Code 的「Yes, and don't ask again」会把密码明文写进一个会被提交的配置文件](https://www.itnews.com.au/news/dont-ask-again-in-anthropics-claude-code-leaks-developer-secrets-630203)**（Apiiro 研究者 Shmulik Cohen 与 Matan Giladi 于 **2026-11-05** 发布，11-06 ~ 11-08 持续发酵）：这条和 11-07 推过的「UA 里带邮箱」不是一回事，风险等级更高。**机制**：当你在权限提示里选「Yes, and don't ask again」，Claude Code 会把**整条被批准的命令原样**写成一条 allow 规则存进 `.claude/settings.local.json`——如果那条命令里带 `PGPASSWORD=…`、`sshpass -p …`、`mysql -p…` 或任何内联 token，它们就以**明文**躺在项目目录里。**规模**：Apiiro 扫到 **103,617 个仓库里的 104,185 个公开副本**，其中 **1,122 个文件（约 1.1%）含至少一个真凭据**，共 **1,379 个**——379 个数据库密码、122 个 Supabase service-role key、103 个 Supabase 账号 token、43 组 SSH 登录、42 个 GitHub / GitLab / npm token、23 个 AWS key、6 个私钥；把 git 历史、fork、共享的 `.claude/settings.json` 与 Agent 聊天日志都算进来，是 **2,539 个凭据、1,994 个仓库、63 个组织**。**为什么 `.gitignore` 没帮上忙**：Claude Code 把该文件加进的是**用户机器上的全局 git excludes**，不是仓库自己的 `.gitignore`，所以保护不会跟着克隆走；它也不覆盖已跟踪文件、`git init` 之前就存在的文件、以及手写的同名文件，`git add -f` 与整目录拷贝直接绕过。**扫描器也漏**：Gitleaks 只标出 1,122 个里的 564 个，TruffleHog 643 个，**215 个两者都漏**——因为嵌在命令里的密码不匹配密钥格式签名。**Anthropic 的回应**：Claude Code 负责人 Boris Cherny 在 HN 上承认「Historically Claude Code has not done secret scrubbing… but we are looking into what we can do」，建议用 auto mode 与密钥扫描，并说修复（auto mode 拦截这类命令、基础密钥扫描）在原型阶段；批评者指出 auto mode 共享同样的暴露面，且分类器会出错。**背景**：GitHub issue #5544 从 2025-08 就报过，被 bot 以 not planned 关掉；对比的 16 个编码 Agent 里，只有 Claude Code 默认把完整命令写进项目文件。**处置顺序很重要**：先把所有曾出现在该文件里的凭据**全部轮换**，再 `git rm --cached`，把 `.claude/settings.local.json` 加进**项目自己**的 `.gitignore`，以后用环境变量/密钥管理器，并尽量批准「命令模式」而不是「整条命令」。
- **[阿里 Co-Design Bench：最强的 Agent 满足了 69.9% 的验收标准，却只完整做完 26.4% 的任务](https://the-decoder.com/ai-coding-agents-still-need-human-cleanup-on-nearly-three-out-of-four-tasks-in-a-real-world-test/)**（阿里 Token Hub 与复旦、浙大、港中文、上海交大、NTU 合作，arXiv **2610.35138** 于 10-26 上传，**11-08** 起被广泛报道）：这个基准和 SWE-bench 的区别在于它考的是**「改一个已经存在的 Web 应用」**——正是前端日常。**怎么造的**：从 39,325 条真实生产请求里去掉重复，留下 37,463 条，再切成 **273 个任务**（100 个多模态编辑 + 173 个仓库级编辑），配 **2,331 条隐藏的专家验收标准**（Agent 全程看不到）；任务特意挑自「用户不得不反复改写需求或回滚改动」的案例。**怎么评的**：judge-then-refute——一个 AI judge 看源码 diff、页面渲染与 **Playwright 浏览器轨迹**，第二个 challenger 专门去挑 stub 与硬编码输出；**严格计分，Partial 不得分**。**结果**（固定 Claude Code harness，3 小时 / 120 轮上限）：GPT-6 Astra 平均通过 **69.9%** 的严格标准，但**只有 26.4% 的任务全部完成**（73.6% 至少漏一条）；拆开看多模态 75.4% / 41.0%，仓库级 66.7% / 17.9%。榜单（标准通过率 / 全通过率）：`gpt-6-astra` 69.9/26.4、`opus-5` 66.1/18.3、`qwen3.8-max` 65.3/16.5、`qwen3.8-27b` 64.4/15.0、`kimi-k3` 62.9/15.8、`gpt-5.6-sol` 61.1/14.3、`opus-4-8` 58.1/10.3、`glm-5.3-flash` 57.3/10.6、`glm-5.2` 56.7/9.5、`grok-4.6` 51.1/6.6。**三个更实用的发现**：任务一旦**同时**涉及布局、设计、交互与内容改动，分数明显掉；GLM-5.2 用掉约 **6 倍** token 却分更低；**harness 影响大到能改变排名**（Qwen3.8-27B 在 Codex / opencode / qwen-code 之间从 56% 到 75%），作者因此建议报结果时必须把「模型 + harness」一起写。⚠️ 三个限制：每个任务只给**一次**请求（不能追问澄清）、AI judge 会误判、26.4% 是对**刻意挑难的压测集**的结果，不能读成「Agent 日常四分之三都做不成」——标准覆盖率也不等于人工清理率。
- **[字节 Seedream 5.5：连续 100 次编辑、原生 RGBA 透明输出](https://toolnavs.com/article/3268-nov-9-ai-briefing-nvidia-board-opens-probe-as-bytedance-ships-seedream-55)**（2026-11-08 发布）：对做前端素材的人，真正的新东西是输出格式而不是画质——**原生 RGBA** 意味着图标、切图、带镂空的插画可以**直接拿到带 alpha 的产物**，不用再走「出图 → 抠图 → 校正边缘」那条流水线；**连续 100 次编辑**且**保留未编辑区域的原像素**，意味着在同一个素材上改文案、换配色不会把整张图重绘一遍（这正是过去「改一个字整张图变样」的根因）；文字损坏率降到 **0.4%**，对做中英文排版类素材是实用指标。⚠️ 目前只有聚合早报与预览流出，官方模型卡、定价与 API 参数未核实，透明通道在导出链路（PNG / WebP）里的保真度也需要自己压测。
- **[百度 ERNIE Evolve：一个会改写自己代码的「自动研究系统」](https://explainx.ai/catch-up-on-ai/2026-11-09)**（2026-11-09 公布）：按公开说法，它是一个**自动化研究系统**——能修改自身实现、迭代实验配置，并在 **NanoChat / NanoGPT Speedrun** 的三个指标上刷出公开最好成绩。这条之所以值得记，不是因为数字，而是因为它把「Agent 做研究」从演示推进到了**有明确、可复现的公开计分板**（Speedrun 系列的价值就在于任何人可以重跑）。⚠️ 目前只有 11-09 的聚合早报转述，**没有找到一手论文、技术博客或代码仓库**；「改写自己的代码」具体改的是训练脚本还是系统本体也说不清，引用前请先找官方材料。
- **[OpenAI 对 Cursor 的模型供应 11-12 到期，这不是新政策但马上生效](https://help.openai.com/en/articles/20001506-using-openai-models-in-cursor)**（2026-08 底宣布，截止日 **11-12**；本周被重新提起是因为日子到了）：OpenAI 以**控制权变更条款**为由结束直接向 Cursor 供模型（Cursor 于 8 月中旬被 SpaceX 收购，交易约 600 亿美元），并表示在收尾期内**不会把包括 Astra 在内的新模型**给 Cursor。Cursor CEO Michael Truell 的说法是 OpenAI 模型只占其用户流量约 **5%**。**官方给的四条出路**：**① BYOK**（自带 OpenAI API key，但**只对本地 Chat 与 Agent 生效**，Cursor Tab / 自动补全、Auto、云 Agent、Automations、Cursor CLI 与 API/SDK 都不覆盖）；**② 在 Cursor 里装 OpenAI 的 Codex 扩展**；**③ 走 AI 网关**（Bedrock / Azure 等 OpenAI 兼容渠道）；**④ 直接换模型**（Anthropic / Google / Grok / 自研）。⚠️ 11-12 之后 BYOK 是否还能用，取决于 Cursor 是否保留该集成、以及 OpenAI 是否允许调用经过 Cursor 的产品链路——两边都没给保证；另有报道称 Anthropic 在消息公布后数小时内就向 Cursor 追加了算力承诺。
