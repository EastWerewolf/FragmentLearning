- **[Antigravity 的 `/swarm`：一个 prompt 拉起一支 Agent 小队，各自在独立 git worktree 里改代码](https://antigravity.google/blog/gemini-4-carbon-in-google-antigravity)**（2026-11-10 随 Carbon 一起预览，CLI **1.5.5**）：这是今天最值得看的产品设计，因为它把「多 Agent」从演示变成了有明确机制的东西。**结构**：一个 coordinator 把任务拆开，拉起若干 worker；**每个 worker 跑在独立的 git worktree 里**，所以并行改同一个仓库不会互相踩文件；另有**对抗式 verifier Agent** 专门去测每一处改动。**协作方式**：共享一块**只追加的消息板**，Agent 之间靠它对齐；**空闲 Agent 会被挂起、不烧 token**；**每个 Agent 可以绑不同模型**——Carbon 负责推理/协调/审计，轻量模型负责并行改动。**交互**：侧边栏有 Swarm UI（Board / Roster / 可回放的 Graph），CLI 里是 `/swarm <task>`、`/swarm board` 或 `Alt+S`；worker 可以 fork、可以换 `/model`、配额耗尽时是**暂停而不是重试**，还有一个 monitor worker 负责报卡住。⚠️ 五个限制：**带 "(Preview & Quota Heavy)" 标签**，每个 worker 都是独立 Agent，**配额消耗远快于普通对话**；**没有公布 Agent 数量上限，也没有 swarm 专属配额规则**；**没有 GA 日期**；**Google 没说「轻量模型」具体是哪几个**；另外只有部分演示（比如 Mountain View 那个鹈鹕游戏）被明确归功于 `/swarm`，其余是普通 Carbon 生成。**读法**：把它当「多 Agent 编排的第一版可用形态」，而不是「已经能无人值守跑完一个仓库」——11-09 那期 Co-Design Bench 的结论（最强模型全通过率 26.4%）仍然是当前的天花板。
- **[MCP 有了固定发布日历：每半年一次，12 月那次推迟到 2027-03-30](https://modelcontextprotocol.io/seps/3398-release-cycle-updates)**（SEP-3398 于 **2026-10-14 Accepted、10-27 合入**；SEP-3392「扩展生命周期」已是 Final，创建于 2026-09-25）：这条改变的是「你该什么时候规划升级」，对把 MCP 放进产品链路的人比任何单个新特性都重要。**节奏**：规范**每六个月发一版，固定在 3 月与 9 月的最后一个周二**。**每版 8 个月周期**：2 个月规划 → Core Maintainer 评审窗口 → 稳定化，**相邻两个周期重叠 2 个月**。**关键里程碑**（相对发布日）：`−8mo` 开始规划、`−6mo` 开放 CM 评审、**`−2.5mo` soft freeze**（进版的 SEP 必须 Final 且合并，含 schema、changelog、参考实现、一致性测试）、`−2mo` 下一周期规划开始、**`−1.5mo` Tier 1 SDK 发 beta**、**`−1mo` hard freeze**（只剩关键安全/互操作修复，且要 Core Maintainer 全员投票）。**最直接的影响**：原本瞄准 **2026-12** 的那次发布**被这条整体推到 2027-03-30**，没做完的提案顺延到后面的周期，而**发布日期本身不会挪**。另有轮值 release manager（secondary 下一周期转 primary）。⚠️ 两点：SEP-3398 目前是 **Accepted 而非 Final**，还差文档与运维侧的落地；SEP-3392 只确认了「扩展生命周期」存在且为 Final，**它的完整分级（Experimental → Beta → Stable → core）在检索结果里只见到标题与状态，正文没有取到**，引用前建议直接看 SEP 原文。
- **[德国主机商 Mittwald 的 MCP 服务器被利用，56 个客户项目受影响](https://webhosting.today/2026/11/09/mittwald-traces-a-breach-of-56-customer-projects-to-its-mcp-server/)**（**2026-11-07** 披露，11-09 起被安全媒体广泛跟进）：这是第一起有明确披露的「MCP 端点本身成为入口」的入侵。**时间线**：攻击者在 **10-21** 探测、**10-23** 表现得像个正常用户、**10-27** 完成利用，**11-04** 才被异常检测发现——**约 8 天未被察觉**。**被拿走的是什么**：**MCP session token**，不是密码；每个 token 都以使用者本人的权限访问 mStudio，所以拿到就等于拿到那个账号的操作能力（API key 也被预防性封禁）。**处置**：MCP 服务器下线并保持离线、token 全部吊销、请外部取证、通报监管；到 11-06 的取证没有发现进一步扩散，**11-07 恢复 mStudio 与 SSH 访问并加了 passkey**。⚠️ 这条最需要克制的地方是 **「AI 辅助攻击」这个说法**：Mittwald 的 MD Robert Meyer 的依据只是日志里「步骤之间只隔几秒」，而多家分析机构指出**脚本自动化同样能做到秒级**，**没有 CVE、没有受影响版本、没有归因**，也**不清楚漏洞在 Mittwald 自己的代码还是开源 MCP 库里**。给你的动作不依赖这个争议：**MCP 的 session token 要当长期凭据来管**（可吊销、可轮换、按会话最小权限），别把它当「一次性的连接票据」。
- **[Playwright MCP 0.0.84：一个浏览器里开多个隔离上下文，Agent 能同时登多个账号](https://github.com/microsoft/playwright-mcp/releases)**（2026-11-11 前后发布）：`browser_tabs` 的 `action: "new"` 现在接受 **`isolatedContext: "<name>"`**——**同名共享同一个 browser context，不同名完全隔离**，不传或传 `"default"` 走默认上下文；cookie 与 storage 相关工具作用于**当前标签所在的 context**。配套的还有 **network inspection 现在保留最多 200 条来自更早导航的请求**。为什么值得单独写：此前多账号/多角色测试要么开多个浏览器实例（profile 锁冲突、并发会话起不来），要么用 `storage_state` 手工切换，一直没干净解；issue #40585 提的就是这件事。⚠️ 这是 **context 级隔离不是浏览器级隔离**——指纹、扩展、缓存策略仍是同一个浏览器实例，做严格的账号隔离测试别把它当等价物；版本号与发布日期在不同聚合站上有出入（有站点写 10-31），**建议以主仓 tag 为准**；另外它的前身工作（playwright-mcp#1530 / #1594）都卡在同一个限制上，这次是否彻底解决，要看你自己的并发场景。
