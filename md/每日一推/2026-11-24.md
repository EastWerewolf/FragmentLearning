### 🌐 语言与规范

- **[W3C 首份公开工作草案：Pointer-driven Animations Module Level 1——指针位置就是时间线](https://www.w3.org/TR/2026/WD-pointer-animations-1-20261124/)**（**2026-11-24** 发布 FPWD，短名 `pointer-animations-1`，编辑 Yehonatan Daniv；同日在 W3C 新闻与 Bramus 的社交账号公布；**目前没有任何浏览器实现**）：**它把「滚动驱动动画」的模型搬到了指针上**：**核心对象 `PointerTimeline`** 是一个 `AnimationTimeline`，带 `source` 与 `axis`，能直接喂给 `new Animation()` 或 `element.animate()`；**CSS 侧三个属性**——**`pointer-timeline-name`**（给时间线命名）、**`pointer-timeline-axis`**（沿哪个轴取指针进度）、**`pointer-timeline`** 简写；再加一个 **`animation-range-center`**，用来把 **50% 进度的焦点**钉在指针的某个位置上。**取值范围**：相对 **viewport**（默认）或**元素自身包围盒**——后者才是「鼠标划过这张卡片、卡片内元素按横向进度依次动」的写法。**它和 scroll-driven animations 共用一套命名时间线的作用域规则**，所以 `timeline-scope` 那套心智可以直接迁移。**能做什么**：视差、聚光灯、跟随光标的进度条、按指针距离分层的动效——**都不需要 JS 每帧算**，交给合成器。⚠️ 四点：**FPWD 只是「拿出去给人挑毛病」**，属性名和语义都会变，**不要照着写生产代码**；**没有实现**，连 flag 都没有，`@supports` 都测不出来；**指针事件与触摸的关系没定**——触屏上「指针位置」是最后触点还是不存在，规范还要讨论；**和 `mousemove` + CSS 变量那套现有做法比**，它的优势是**能进合成器**，但前提是浏览器真的按时间线实现，而不是每帧回主线程。

### 🎨 浏览器与 CSS

- **[Firefox 161 正式发布：按站点开关的内置 VPN、经典主题，以及平台侧的 HTTP 压缩字典传输](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/161)**（**2026-11-24** 14:00 UTC 发布，首日 25% 灰度；同日 **ESR 153.8 / 115.46**；11-22 那期推过 beta 清单，这里只写**发布版确认**与当时没写到的三条）：**平台侧最该关注的一条是 `HTTP Compression Dictionary Transport`**——服务端用 **`Use-As-Dictionary`** 声明一份可复用的字典，客户端在后续请求带 **`Available-Dictionary`**，响应就能用 **`dcb` / `dcz`** 编码。**它的意义**：**跨请求的共享压缩字典**，对「每次只改一点点的 HTML / JS / CSS」能显著减少传输字节，是 Brotli 之后最实质的一次压缩协议扩展——但**要服务端与 CDN 一起改**，前端单方面吃不到。**其余平台项**：**CSS `random()`**（含可选的步长与 `<random-key>`）、**`var()` / `attr()` / `env()` 首参里的嵌套替换函数**、**CSS Typed OM 支持**（`CSSColorValue` / `CSSRGB` 这些颜色接口仍缺）、**SVG `<image>` / `<script>` / `<feImage>` 上的 `referrerpolicy`**、**异步剪贴板的自定义格式**（`web ` 前缀的 MIME，同源可读）、**`NavigationTransition.to`**、**WebTransport 的 `anticipatedConcurrentIncoming*Streams`**、**`RTCRtpSender.setParameters()` 的 `setParameterOptions`**（同一次调用里请求关键帧）。**还在开关后**：跨文档视图过渡 + `blocking` 属性、`margin-trim`、`text-autospace-size`。**产品侧**：**内置 VPN 可按站点设「总是开 / 总是关」**（旧排除列表会转成「总是关」；Mozilla 从 11-10 到 2027-01-31 取消了 VPN 流量上限）、**经典主题**（Proton、Firefox OLED、纯色）、**复制当前标签 URL 的快捷键**（默认不绑）、**应用菜单里的标签组**、**导入 Chrome 历史带访问频次**、**地址栏建议带「上次查看」这类原因标签**。⚠️ 四点：**25% 灰度**，企业按 ESR 排期；**压缩字典是「服务端 + CDN」的工程**，浏览器支持只是前提；**`<meta name="color-scheme">` 影响 `prefers-color-scheme`** 这类行为变更在 11-22 那期已提醒，正式版照旧；**Android 的 `backdrop-filter` 在部分设备上明显变快**，是渲染路径修复，不是新特性。

- **[Chrome 160 把 WebMCP 的 `RegisteredTool` 换成 `Tool` 接口：早期试验代码会直接断，试验期延到 Chrome 162](https://ppc.land/googles-change-to-chromes-ai-agent-feature-breaks-early-testers-code/)**（Chromium 的 CL 在 **10-15** 提交、以 `14b6d53` 合入，随 **Chrome 160** 的 Dev 通道出现（当前 **160.0.8157 / 8171** 一带，稳定预计 **12 月中旬**）；blink-dev 的「Intent to Extend Experiment」在 **09-28** 提交，试验从 **Chrome 149–156** 延到 **Chrome 162**，**token 到期 2027-03-30**；使用率上限从 **0.5% 提到 2.0%**）：**这是一次「不改会静默错」的 API 变更**。**改了什么**：`getTools()` 返回、`executeTool()` 接收的对象**从字典 `RegisteredTool` 变成接口对象 `Tool`**，每个 `Tool` 带一个**不暴露给网页的 `tool_id`**，`executeTool()`（含跨文档执行）**按 ID 而不是按名字**定位。**为什么**：修一个**执行时的重注册竞争**——以前页面注销一个工具、再用同名注册新的，**拿着旧 `Tool` 去执行会跑到新工具上**；现在会直接拒绝。**谁的代码会断**：还在传「名字 + 字典」的；还在用 `navigator.modelContext`（Chrome 150 已弃用、7-9 从 Chromium 移除，现在是 `document.modelContext`）的；还在 `window.ontoolactivated` / `ontoolcancel` 上监听的（**Chrome 156 起失效，要挂到 `document.modelContext`**）。**新增的 WPT** 是 `webmcp/imperative/tool-re-registration-race.https.html`。**还没修完的**：embedder 与 DevTools 仍走 `ExecuteToolByName()`，**一样受这个竞争影响**；`toolactivated` / `toolcancel` 目前仍只按名字标识工具（issue #349 / #384）。⚠️ 四点：**这是 Origin Trial 里的实验 API**，不稳定是它的常态，**别把它写进对外承诺**；**「按 ID 执行」意味着工具一旦重注册，旧引用必须丢弃**，缓存 `Tool` 对象的代码要重新取；**声明式表单 API 的口径有点乱**——规范侧 10-08 说「暂时移除」，Chrome 仍在发，按 Chrome Status 为准；**试验延长到 162 不代表会 Ship**，官方仍只说「希望在窗口内提交 Intent to Ship」。

### 🤖 AI 与开发

- **[Anthropic 发布 Claude Ship：Code Review、PR Steward、Claude Approvals——让 Agent 按仓库里的自然语言策略自动批准 PR](https://techcrunch.com/2026/11/23/anthropic-launches-claude-ship-letting-ai-agents-review-fix-and-approve-code-changes/)**（**2026-11-23** 发布；面向 **Claude Team / Enterprise**，跑在 **GitHub** 上；Code Review **GA**、PR Steward 与 Claude Approvals **beta**；Claude Code 里新增 **`/ship`** 命令）：**三件套的分工很清楚**：**① Code Review**——从多个视角审 PR，并**对自己的发现做对抗式复核**（GA，可选 Quick / Standard / Deep 三档）；**② PR Steward**（beta）——**修 CI 失败、解合并冲突、处理 Code Review 的意见**，每次 push 后留评论并给回滚说明，**但它不能批准、也不能合并**；**③ Claude Approvals**（beta）——**按团队写在仓库里的自然语言策略自动批准**例行改动，官方定位是「更聪明的 CODEOWNERS」。**Anthropic 给的用法很克制**：**先让 Approvals 跑 observe-only**，看它想批什么，再考虑把它设成 branch protection 的必需检查；从一个仓库开始、设月度花费上限。**计费**：按 token，**Approvals 没有基础费**；**Enterprise 组织在 2027-01-15 前可领 ≥$10,000 额度**；**Zero Data Retention、HIPAA、客户自管密钥（CMEK）配置不可用**。**动机**：官方说 Claude Code 团队「大部分代码是 Claude 写的」，于是 PR 之后的环节成了瓶颈；内部数据是 **6–9 月合并的 PR 翻倍、被回滚的改动占比降了 40% 以上**。**产品自带的警告**：它「使用 AI，可能漏掉 bug、安全漏洞或其它问题」。⚠️ 四点：**「自动批准」是这轮里风险最高的能力**——策略文件写宽了等于没有审查，写窄了就是人工重复劳动，先跑 observe-only 不是建议是必须；**报错的内部数据是 Anthropic 自述**，没有对照组；**PR Steward 不能合并**这条边界要写进流程，否则团队会以为它可以兜底；**它只在 GitHub 上**，GitLab / Bitbucket 用户这轮用不上。

### 📚 好文精选

- **[Simon Willison《Select Styling Specimens》：让 Claude 生成一张覆盖所有 `<select>` 样式的测试页，再挑出跨浏览器最稳的那套 CSS](https://simonwillison.net/2026/Nov/22/select-styling/)**（**2026-11-22**；起因是他觉得 Chrome 里的 `<select>` 「挺丑」，于是让 Claude 生成一个「展示 select 所有可样式化方式」的页面，自己拿去每个桌面 / 移动浏览器截图对比）：**这篇的价值不在那几行 CSS，而在「用生成式工具做跨浏览器取证」这个工作流**。**他最后选中的方案**：**`appearance: none`** 去掉原生外观 + **内联 SVG data-URI 画箭头** + 统一的 padding / 边框 / 圆角：

  ```css
  select {
    appearance: none;
    color: #1f2933;
    padding: 0.5em 2.25em 0.5em 0.75em;
    border: 1px solid #c4cbd3;
    border-radius: 6px;
    background: #fff url("data:image/svg+xml,...") no-repeat right 0.75em center / 0.75em;
  }
  ```

  **它的代价写得很明白**：**`appearance: none` 是「用一致性换掉原生行为」**——焦点环、禁用态、深色模式、高对比度模式、以及各平台的原生下拉面板，都要自己补回来。**这篇真正可抄的方法是三步**：**① 让模型先枚举「所有能改的地方」而不是直接给答案**；**② 把产物当测试夹具（fixture）拿去真浏览器截图**；**③ 由人做取舍**。⚠️ 三点：**那段 CSS 没有 `:focus-visible` 焦点环**，直接上线会伤键盘用户；**`appearance: none` 不会改变弹出层的原生行为**，移动端的下拉面板仍是系统控件；**这是单人的抽样对比**，不是兼容性矩阵，结论按方向看。
