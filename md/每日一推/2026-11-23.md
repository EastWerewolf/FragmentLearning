### 🎨 浏览器与 CSS

- **[WebKit 放出 spatial CSS 开发者预览：`<model>` 用 CSS 布局摆进你的房间](https://webkit.org/blog/18621/introducing-spatial-css-a-developer-preview/)**（**2026-11-16** 发布，随 **visionOS 27.3** 的 Safari 提供；规范是 **CSS Spatial Layout Module Level 1** 的 Editor's Draft（同日，Apple 独占编辑）；**默认关闭**，需在 设置 → App → Safari → 高级 → 功能标志 里打开 **CSS Portals**）：**它是「3D 内容第一次真正走 CSS 布局管线」而不是 WebGL 场景**。**六个构件**：**① `spatial: portal`**——把一个 `<div>` / `<figure>` 声明成**子元素共享的 3D 空间**；**② 3D `transform`**——同一个 `DOMMatrix`，但在 portal 里是**真的三维变换**；**③ `position-anchor` + `position-context: anchor`**——因为 `<model>` 是空元素**不能嵌套**，模型要挂到另一个模型内部的参考点上，就靠锚点定位；**④ `@environment-map`**——用 360° HDR 全景图定义可复用的光照环境，取代原来的 HTML 属性；**⑤ `portal-action: orbit`**——允许用户旋转 / 环绕场景（`pan-x` / `pan-y` 标为将来）；**⑥ `requestVolumetricScene()`**——把这个 portal 提升成「连通体积场景」，直接摆进用户房间，且**与页面保持实时联动**。**`<model>` 本身已经在 Safari 27 全平台 GA**——这次预览加的是「怎么摆」。**怎么试**：visionOS 模拟器（Xcode）里就能跑，不用真机。⚠️ 四点：**只在 visionOS**，iOS / macOS 没有；**编辑草案 + 默认关闭**，属性名与语义都可能改（报道里还列了 `portal-stage`、`front-limit`、`environment-intensity`、`z-align-self` 这些未文档化的属性）；**iframe / 跨源下的行为还没定义**，别把它当安全边界；它和 WebXR 不是一回事——**这是声明式排版，不是帧循环**，做游戏仍要走 WebGL / WebGPU。

- **[Firefox 161 明天（11-24）稳定：`random()` 之外，还补了 SVG `referrerpolicy` 与剪贴板自定义格式](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/161)**（稳定 **2026-11-24** 14:00 UTC 发布，首日 **25%** 灰度；同日 **ESR 153.8 / 115.46**；11-23 是 iOS 版提交 App Store 与合并到 162 的日子，**不是桌面版发布日期**）：**11-22 那期已按 nightly 说明推过 beta 清单，这里只补这周新确认的三条**：**① SVG 元素支持 `referrerpolicy`**——内联 SVG 里的外链请求终于能单独控制 referrer，和 `<img>` 对齐；**② Clipboard API 支持自定义格式**——除了 `text/plain` / `text/html`，可以写自定义 MIME；**③ `NavigationTransition.to`**——在**跨文档**导航的视图过渡里拿到目标文档的 URL。**另有实验性的一条**：**跨文档视图过渡**（同源导航之间做 View Transition）进了实验开关。**产品侧还多了一条**：**经典主题与 OLED 纯黑主题**进了主题选择器。**修的部分沿用 beta 清单**：WebRTC 低分辨率 H.264（158 起回归）、标签组删掉后会话恢复失败、Canva Docs 里输入法只出首字母、全屏被 Windows 任务栏压住；**Android 的 `backdrop-filter` 在有问题的设备上明显变快**。⚠️ 三点：**25% 灰度意味着当天只有四分之一用户拿到**，企业环境要按 ESR 排期；**`referrerpolicy` 只对内联 SVG 里的请求生效**，`<use>` 引来外部内容的情况要看具体路径；**跨文档视图过渡仍是实验**，且不同源会直接跳过，别按「全站可用」设计。

- **[CrUX 11 月版再加两个实验指标：带 soft navigation 的 FCP 与导航类型](https://developer.chrome.com/docs/crux/release-notes)**（**2026-11** 的 CrUX 发布；背景是 Chrome **151**（7-28）默认开启 Soft Navigations API、CrUX 从 **10-13** 起发布带 soft nav 的实验版 CWV）：**这件事对 SPA 的「真实分数」影响很大，但还没进正式指标**。**本次新增**：`experimental_first_contentful_paint_with_softnavs` 与 `experimental_navigation_types_with_softnavs`（先上 **CrUX API / CrUX Vis**，BigQuery 下月跟进）；此前的三条是 LCP / INP / CLS 的 `_with_softnavs` 版本。**数字为什么重要**：**约 70% 的 origin 几乎没有 soft nav 流量**，所以整体通过率只从 **56.3% 升到 60.3%**；但**soft nav 占比 75–100% 的 Android origin，LCP「Good」从 26% 跳到 87%**——一个纯 SPA 的站点，在旧口径下被首屏那次冷加载「判了刑」。「**它是实验字段，不进稳定分、也不影响搜索排名**」，Google 的目标是 **2027 年 5 月**左右转正，之后 Search Console 再跟。⚠️ 三点：**别拿实验字段去做 KPI 报表**，字段名带 `experimental_` 就是随时会改；**soft nav 的边界由浏览器判定**，你用 History API 手搓的路由不一定被识别；**INP 在近期数据里仍有回退**，Chrome 没给确定原因，优化时别只盯 LCP。

### 🚀 框架与工具链

- **[Vercel 给 Feature Flag 加部署检查：代码里有、项目里没定义的 flag 会让部署直接失败](https://vercel.com/changelog/catch-missing-feature-flags-before-they-reach-production)**（**2026-11-23** 发布；**所有套餐可用**，需在 项目 → Build and Deployment → Deployment Checks 里打开并勾「必需」）：**它堵的是一个很具体的坑**：代码里 `flag('new-checkout')`，但 Vercel 项目里从没建过这个 flag——以前**不报错，直接回退到 flag 的默认值**，于是本该关着的功能被打开。**机制**：部署**就绪时**读 **Flags SDK 的发现端点**（通常是 `/.well-known/vercel/flags`），把「代码声明的」与「项目已定义的」对齐，**缺的会在检查结果里列出来**，补建后重新部署即可。**前置条件**：项目里要设 **`FLAGS_SECRET`**，且发现端点要暴露出来。**它和 Flags 面板里的三个徽标是同一套逻辑的硬闸**：**Drafts**（代码有、面板没有）、**Unreferenced**（面板有、最新生产部署没有）、**Referenced archived**（引用了已归档的）。⚠️ 四点：**「缺 flag 就打回」对多人分支是好事，对「先合代码、后建 flag」的团队是流程变更**——要么先建后合，要么把这个检查设成非必需；**它读的是发现端点**，端点鉴权配错会误报；**默认值是 `false` 才安全**，如果你的 flag 默认 `true`，这个检查挡住的只是「名字打错」，不是「功能误开」；**它只管 Vercel Flags**，自建 flag 服务（LaunchDarkly / Unleash）不在范围内。

### 🤖 AI 与开发

- **[OpenAI 放出 `GPT-Live-1.1`：只走 `v1/live/sessions`，待机 5–60 秒后自动降档到 $0.02/分钟](https://developers.openai.com/api/docs/models/gpt-live-1.1)**（**2026-11-19 ~ 11-20** 进 API；替代 GPT-Live-1 成为语音接口的默认档，后者 5 周前已先进 ChatGPT Voice）：**它解决的是「真人对话里大部分时间没人说话，但全双工模型仍在烧钱」这个账**。**计费拆成两档**：**活跃 $0.05/分钟**、**待机 $0.02/分钟**（按秒计），待机比原来便宜 **60%**。**待机怎么触发**：会话对象里配 **`session.wake_policy.type: "speech"`**（等用户开口才开始推理，而不是连着就开始）、**`idle_timeout_s`（5–60 的整数）**——这么多秒内没有输入 / 输出转写就回待机；还有 **`wake_policy.vad_threshold`（0–1，默认 0.5）**。**事件**：`session.paused`（超时停推理）与 `session.resumed`（恢复，含首次唤醒）。**只在 WebRTC 上成立**：麦克风轨道保持、连接与会话 ID 保留、**恢复时对话历史自动回来、不用重新鉴权**；WebSocket / SIP 的官方建议是**关掉重开**。**两个坑要提前算**：**建会话按 15 秒时长计费**（会话真跑起来后会抵扣）；**从待机唤醒后的第一句响应会变慢**，因为推理要重启。⚠️ 四点：**`v1/live/sessions` 是独立端点**，不是 `v1/realtime` 的别名，迁移要改代码；**待机省的是钱不是体验**，对延迟敏感的客服场景要么关掉待机、要么把 `idle_timeout_s` 调短；**WebRTC-only 意味着服务端直连方案（SIP 电话）用不上这套折扣**；参数名以官方 reference 为准，第三方整理里 `wake_policy` 的字段顺序与默认值有出入。

- **[OpenAI 后台模式新增 2 小时 / 8 小时完成窗：同一批 token 便宜 30% / 40%](https://community.openai.com/t/reduce-costs-using-background-mode-with-completion-windows/1418130)**（**2026-11-17** 进 API changelog，公开 beta；适用 **GPT-6.2 Astra / Sol、GPT-6.1 Terra、GPT-6 Luna**）：**它是把「Batch 的折扣」搬进「有状态的 Agent 链」**。**用法**：`background: true` + **`background_options.completion_window: "2h" | "8h"`**（默认 `soonest` 无折扣），`service_tier` 必须是 `default`。**折扣**：**2 小时窗 −30%、8 小时窗 −40%**（相对标准价）；**后续请求只要复用同一个 `continuation_id`、模型、项目、窗口与后台设置，也享受同档折扣，并拿到更高队列优先级**。**三条硬限制**：**不能流式**（只能 webhook 或按 ID 轮询）；**2h / 8h 请求与 Batch 共用限流**（提交时按输入 token 计）；**完成窗不是 SLA**，只是目标。**缓存也被隔开**：2h / 8h 请求写的 prompt cache **不能被 Standard 请求复用**，反之亦然。**还有一个方向性变化**：**从 GPT-6.2 Astra / Sol 起，新模型不再提供 Flex 处理**——「慢一点、便宜一点」的长任务被引导到这两个窗口。⚠️ 四点：**Batch 仍是 50% 折扣（24 小时）**，独立批处理用它更划算；**Agent 链要复用 `continuation_id`**，你自己拆请求就吃不到折扣；**后台模式即使 `store: false` 或开 ZDR 也会临时存响应数据**，合规评审要过一遍；**8 小时窗的「目标」不等于「保证」**，排期别写死。

- **[Hugging Face 的 harness adapters：把 LoRA 训进 Agent 壳里，Qwen3.8-27B 在 Terminal-Bench 2.1 上 39% → 55%、token 减半](https://huggingface.co/blog/harness-hub/harness-adapters)**（**2026-11-20** 发布；产物在 HF 的 **`harness-hub`** 组织下，**Apache-2.0**）：**它是 11-18 那期「harness 比模型更能决定成败」的直接续集**——那次是**测**壳，这次是**把模型训到壳上**。**做法**：用 **TRL 的 `AsyncGRPOTrainer`（GRPO）**在**真实 Agent 壳里**训 **rank-32、全线性挂载**的 LoRA，三个壳分别是 **Pi 1.5.2、OpenCode 2.2.7、Hermes Agent v0.22.6**；训练集约 **871 个可验证编码任务**（其中 **171 个合格**），配一个 **safeagents** 工具调用护栏，**2×B200**、学习率 2e-5、思考关掉。**关键数字**：**Pi 专家适配器在 Terminal-Bench 2.1 上 39% → 55%**，每任务 token 从约 **2.9K 降到 1.5K**；把三个 rank-32 适配器**按 ½ 权重合并成 rank-96 的 super-adapter** 后，六个「壳 × 基准」组合的均值 **39.5% → 49.0%**（思考关）、**55.5% → 63.5%**（思考开），工具调用次数降 **53–73%**。**一个反直觉的结论**：**思考关闭时，各壳自己的专家适配器通常打赢 super-adapter**（Pi 尤其明显）；**思考打开时才反过来**。**还有一个负面结果**：给 Claude Code 做的适配器（只对 LFM2.5-24B-A2B）**没有收益**。⚠️ 四点：**全部为厂商自测、每任务单次尝试**，跨壳数字不可横向比；**合并权重是在 Terminal-Bench 2.1 上调的**，对那一个基准略偏乐观；**模型卡里有过一轮更正**（Pi 的 SWE-bench Pro 从 29.4%→62.7% 改成 39.2%→64.7%，原因是隧道失败与 token 上限），引用前看最新卡；**这说明「适配器 + 壳」正在变成一种交付物**——以后选模型可能要连着选它的壳适配器。

- **[微软 Foundry 的 model router 扩到 45 个模型，`model: "auto"` 进预览](https://learn.microsoft.com/en-us/azure/foundry/openai/concepts/model-router)**（路由版本 **2025-11-18**，文档随 **Ignite 2026（11-17 起）** 更新；官方口径 45 个，Ignite 的宣传口径是「前 50」）：**它和 11-20 推的 Foundry Toolbox 不是一回事**：Toolbox 管**工具怎么打包与版本化**，router 管**一次请求该落到哪个模型**。**现状**：45 个模型横跨 OpenAI、Anthropic、微软 MAI、xAI、DeepSeek、Meta、Fireworks，**11 月新增 8 个**（含 `claude-opus-5-5` / `claude-haiku-5-5`、`deepseek-v4.1-flash`，以及报道提到的 **GLM-5.3**）。**新模式**：**`model: "auto"`** 预览——不建 deployment，直接用 router；**默认 Balanced**，另有 **Cost**（质量差约 5–6%）与 **Quality**。**路由是两段式**：先按请求要求过滤（要不要 tools、输出格式、图片），再排序；**按请求控制**用 `Foundry-Features: ModelRouterControls=V1Preview` + `routing_config`，**会话粘性**也在预览。**支持的 API**：Responses、Chat Completions，以及**仅 Claude 模型可用的 Messages API（预览）**；客户端侧明确列了 **Claude Code、Codex、OpenCode、GitHub Copilot**（`copilot --model foundry/model-router`）。⚠️ 四点：**45 与 50 的差是「文档已上线」与「Ignite 承诺」的差**，排期按 45；**Cost 档的质量差是微软自己给的区间**；**Claude 模型必须部署在同一个 Foundry 资源里**，跨资源路由会失败；**每个 router 版本都有自己的退役日**，升级不是自动的。

- **[《Web-Perf Wednesday 018：soft navigation 把 CrUX 通过率抬起来了》](https://csswizardry.com/2026/11/web-perf-wednesday-018-soft-navigations-lift-the-crux-pass-rate/)**（CSS Wizardry，**2026-11**；与 CrUX 11 月版的实验字段同一批数据）：**这篇的价值是把「SPA 到底被首屏冤枉了多少」量化出来**。**它做的事**：把 CrUX 的**标准 CWV** 与 **`_with_softnavs` 实验版**逐字段对照，按 **soft nav 流量占比**分桶看差值。**结论写得很克制**：**约 70% 的 origin 几乎没有 soft nav**，所以大盘只动了两三个百分点；**真正被误判的是「几乎全是 soft nav」的 SPA**——那一桶的 LCP「Good」比例从 **26% 跳到 87%**，**整体通过率 56.3% → 60.3%** 基本都是这一桶贡献的。**对工程的三个用法**：**① 先看你的 origin 在 CrUX Vis 里的 soft nav 占比**，低于 10% 的话这件事跟你关系不大；**② 别用实验字段做对外承诺**，它是给「诊断」用的；**③ 如果你的 SPA 在旧口径下被判 LCP 差**，可以拿实验数据向业务解释「不是变快了，是终于按路由计了」。⚠️ 三点：**soft nav 由浏览器判定**，History API 手搓的路由、跨源跳转、带整页刷新的「假路由」都不算；**实验字段的采样与聚合口径会变**，同一天不同工具读到的数可能不同；**转正目标是 2027 年 5 月**，在那之前 Search Console 不会用它。
