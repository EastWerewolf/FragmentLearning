### 🎨 浏览器与 CSS

- **[Firefox 160 beta：`random()` 落地，锚点定位开始把锚点的 transform 算进去](https://www.firefox.com/en-US/firefox/160.0beta/releasenotes/)**（11-05 已推过「稳定版 11-10」这个时间点，这里补 beta / Nightly 里的具体特性清单）：对写 CSS 的人来说有两条是实打实的新能力。**一是 `random()` 函数**（Bug 2071165）——可以在任何允许数学函数的位置生成一个区间内的随机值，并支持可选的步长参数，意味着过去要靠 JS 或预生成一堆类名才能做的随机抖动（位置、延迟、旋转角）现在能写进样式表；注意它是**每次计算时取值**，所以和 `@property`、动画配合时要自己控制「什么时候重算」。**二是锚点定位的修正**（Bug 2059840）——从 160 起，Firefox 在给被锚定元素定位时会**把锚点元素自身的 `transform` 一起算进去**，这对用 `@position-try` 手写浮层、又给触发按钮加了缩放/位移动效的组件是关键修复，之前会飘。其余值得记：**Web Speech API 的语音识别实现**（端上实时转写，约 40 种语言）、**`::-webkit-input-placeholder`** 作为 `::placeholder` 的别名支持（冲着兼容老站点去的）、macOS 上 **WebGL 改走 Metal**、Android 默认开启 **Local Network Access** 限制、**MKV**（含 FLAC/MP3/PCM）播放、PDF 导出带无障碍 MathML。实验功能（默认关）：**CSS Typed OM 算术** `CSSNumericValue.add() / .sub() / .mul() / .div()`，开关 `layout.css.typed-om.enabled`。⚠️ 这是 beta 说明，功能与开关名在 11-10 正式版前仍可能变；`random()` 的求值时机与可复现性建议自测后再用。

### 📚 好文精选

- **[Google：一条过期的 `TODO(bug/…)` 让 Agent 多走 70% 的步、多烧 77% 的 token](https://developers.googleblog.com/en/agent-distraction/)**（Google Developers Blog，2026-11-06，作者 Sam Saccone 与 Madhuri Garikapati；分析 **91.3 万+** 编码 Agent 会话）：这是我这个月读到最可操作的一篇，因为它把「Agent 为什么绕远路」量化了。链路是：**13%** 的会话让 Agent 看到了行内的 `TODO(bug/…)` / `FIXME(bug/…)` 引用 → 其中 **6%** 的遭遇里 Agent 真的跑去处理那个 bug → **83% 是开发者根本没要求**。而这些未经要求的「跑偏」里，**41% 追的是已经关闭的工单**（32% 已修复/已验证、9% 过时或 won't fix、2% 重复或受限），**57%** 是仍然开着的 bug 并**扩大范围**（其中 61% 只查不改，39% 真的动了代码）。代价：有这类未受要求跑偏的会话，平均多 **70% 步骤、77% token、105% 等待时间**。Google 的处置是让清理 Agent 批量删过期引用，**人工审核接受率 >95%**。**给你的动作**：`TODO(bug/123)` 这种「带链接的注释」对 Agent 是强诱饵，比普通 TODO 危险得多；如果团队用 Issue 编号当待办，要么在 `TODOs` 里写清楚「别看」，要么在 Agent 的上下文规则里显式排除。
- **[GitHub：一周 12 亿次 commit，然后卡在 review 上](https://dev.to/tiaforge/12-billion-commits-a-week-still-stuck-in-review-the-four-stages-of-agentic-engineering-1jek)**（GitHub Blog 的《Beyond code generation: A developer's guide to agentic engineering》，作者 Nick Liffen，约 2026-11-06；上面链接是二手精读）：数字很刺眼——GitHub 在 **10 月的某一周**收到 **12 亿+ 次 commit**，比一年前多 **400%+**，比 2025 年全年加起来还多。它的论点不是「AI 太强」，而是那句「**写代码变快了，围着代码的活没变快**」，并引 **Faros AI** 的统计作为证据：团队从低 AI 采用率升到高采用率时，PR 在 review 里停留的时间涨了 **441%**。方法论部分是 **Plan → Build → Verify → Observe** 四段，把 Copilot 的 Plan Mode、agentic workflows、云沙箱、stacked PR、Copilot code review 一一挂上去。⚠️ 三点保留：**这是厂商文档**（为 Copilot 站台）；**12 亿是原始 commit 量**，不等于合入或交付的量；**441% 是引用第三方研究**，不是 GitHub 自己的遥测。真正该换的指标是你自己的 **review 队列深度 / 每个合并 PR 的 review 时长**，而不是 commit 数。
- **[Cloudflare：Privacy Pass 会遇到量子问题，而 ML-DSA 换不进盲签名](https://blog.cloudflare.com/vole-mole/)**（Cloudflare Blog，约 2026-11-06，Bas Westerbaan 等）：给做隐私限速、防滥用的团队一条技术长文。**问题**：Privacy Pass 用了约十年（iCloud Private Relay、Privacy Gateway 都在用），靠经典 RSA / 椭圆曲线**盲签名**签出不可关联的令牌；量子攻击者能伪造令牌从而绕过限速——不过**兑换环节对量子对手仍然无条件不可关联**，这点常被误解。**障碍在体积**：ML-DSA-44 签名 **2,420 字节**，ECDSA-P256 只有 64 字节，盲签名没有「直接替换」这条路。**提出的 MOLE**（Moderation Of unLinkable Endorsements）转去隐藏**签发者**身份：由 anchor 签发、moderator 兑换，客户端证明它来自一个可信锚点集合中的某一个而不暴露是哪个，这样所有客户端受同等对待。**密码学底座**是 VOLE-in-the-Head 非交互 ZK + 多元签名（UOV / MAYO）；把 PoMFRIT 构造里的 MAYO 换成 UOV 后，盲签名从 **6.7KB 降到 4.3KB**（代价是公钥更大）。参考体积：VOLEitH 的 FAEST 约 4KB、KuMQuat 约 2.6KB，UOV 签名约 135 字节但公钥 46.6KB。⚠️ 这是**研究方向，不是已交付的产品**；Cloudflare 只说在做面向 agent 流量的下一代私有认证。
